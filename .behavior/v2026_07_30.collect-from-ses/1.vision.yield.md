# vision: collect-from-ses

> the wish: enable folks to provision the resources required to **send** and **read**
> email for a domain they own. see `0.wish.md`.

> **scope (confirmed by wisher):** do **both** — the mail infra AND the gatherer `ses` adapter
> (read + send), then **demonstrate the whole loop on `jelly@one.nheuron.com`**, the same way
> declastruct-aws dogfooded `echo@demo.ehmpathy.com`.
>
> **update — the infra is now REAL, not assumed.** declastruct-aws has **published** all the
> ses + s3 resource types AND shipped a live dogfood
> (`provision/aws.infra/account=demo/resources.mail.ts` stands up `echo@demo.ehmpathy.com`,
> receives to s3, sends out, replies via an `echo.reply` skill). so deliverable (a) is no
> longer "author net-new declastruct resources" — it is **consume the published resources** to
> declare the `jelly@one.nheuron.com` mailbox, mirrored on the demo provision file.

---

## the outcome world

### day-in-the-life

vlad owns `nheuron.com` on cloudflare. he wants a mailbox for **jelly** — a clone that reads
and answers — without a google workspace, without an oauth dance, without a service account
that can impersonate every mailbox in the org.

two moves, one mechanism:

```sh
# read: collect mail sent to jelly's mailbox
rhx gather.mail --from ses --address jelly@one.nheuron.com --since 2026-08-01

# send: answer a gathered mail from the same address (respond path)
rhx gather.reply --from ses --address jelly@one.nheuron.com --to alice@example.com
```

> **scope note on send:** `gather.reply` illustrates the *capability*, not a committed CLI
> surface. the concrete send deliverable in this behavior is the `setReplyViaSes`
> communicator (`ses:SendRawEmail`). whether it is exposed as a `gather.reply` skill now or
> deferred to a follow-up is a roadmap decision — the vision commits to *send works from the
> mailbox identity*, not to a specific skill name.

mail sent to `jelly@one.nheuron.com` lands in an s3 bucket as raw rfc822; the gatherer
reads + parses it. jelly answers from the same address via `ses:SendRawEmail`. auth is
plain iam — the `AWS_PROFILE` from keyrack, scoped to the `nheuron-prep` account.

the address reads as its own sentence: *jelly, a clone, one connection into the external
brain* (see `domain.terms/one.md`).

### before/after contrast

| before | after |
|--------|-------|
| stand up a google workspace to give a clone a mailbox | reuse a domain you already own |
| service account with domain-wide delegation (reads *every* org mailbox) | a mailbox scoped to one address |
| oauth device flow, 7-day token expiry, re-auth weekly | iam via `AWS_PROFILE`, no token expiry |
| read-only — the clone cannot answer | bidirectional — read AND send |
| click through consoles by hand, hope it is reproducible | declared resources, idempotent get+set |
| one shared account holds it all | nested vaults — org, account, subdomain, mailbox, grant |

### the "aha" moment

"wait — i can turn a subdomain i already own into a mailbox my clone both reads and answers
from, authed by the same `AWS_PROFILE` i already use? no workspace, no oauth, no weekly
re-auth?"

## user experience

### usecases

| usecase | goal |
|---------|------|
| provision a clone's mailbox | declare send+read infra for a domain i own |
| read the clone's mail | collect mail sent to that one address |
| respond as the clone | answer a gathered mail from the same address |
| **demonstrate on `jelly@one.nheuron.com`** | **dogfood the whole loop on a real mailbox, like the demo did with `echo@demo.ehmpathy.com`** |
| reuse for another domain | re-run the same declared resources for a new mail-domain |
| tear it down | del the declared resources when the mailbox is retired |

### the four deliverables

**(a0) the nheuron aws account triplet** — `nheuron-root` (org manager, bootstrapped by hand),
plus `nheuron-prod` + `nheuron-prep` (declared members). the layout mirrors a peer repo that
already runs this exact triplet, and the account declaration mirrors
`provision/aws.auth/account=.root/resources.demo.account.ts`:

```
provision/aws.auth/
  resources.common.accounts.ts        # the 3 env-sourced root emails; THROWS at module load
  account=.root/
    bootstrap.md                      # the by-hand steps: create nheuron-root, create the org
    resources.prod.account.ts         # DeclaredAwsOrganizationAccount 'nheuron-prod'
    resources.prep.account.ts         # DeclaredAwsOrganizationAccount 'nheuron-prep'
    resources.admin.sso.ts            # sso access to each
    resources.scp.ts                  # org-wide guardrails
    resources.ts                      # the aggregate
  account=prod/  resources.oidc.ts + resources.ts
  account=prep/  resources.oidc.ts + resources.ts
```

each declared member account takes the researched shape:

```ts
DeclaredAwsOrganization          managementAccount = RefByPrimary({ id: <root id, read at
                                   apply time from the provider's own credentials> })
                                 featureSet = 'ALL'
DeclaredAwsOrganizationAccount   name = 'nheuron-prep'      // and 'nheuron-prod'
                                 email = <env-sourced; its natural key>
                                 iamUserAccessToBilling = 'ALLOW'
                                 roleName = 'OrganizationAccountAccessRole'
                                 tags = { managedBy: 'declastruct', purpose: 'prep' }
```

the `prod` / `prep` split follows `prefer.env_access.prep_over_dev` — prep is pre-production,
where the mail demonstration lands; prod is reserved for real traffic.

> **⚠️ `nheuron-root` is bootstrapped BY HAND, not declared.** declastruct cannot mint the
> organization it authenticates as — so a human creates the root account and clicks "Create an
> organization" once, per a `bootstrap.md`. from there the apply runs **as the root** and mints
> `nheuron-prod` + `nheuron-prep` declaratively.
>
> so the sequence is: (0) bootstrap `nheuron-root` + its org by hand → (1) apply the account wish
> as the root → prod + prep exist → (2) assume into `nheuron-prep` → apply the mail wish (a)
> there. the `account=.root/` vs `account=prep/` split in the tree above IS this seam.
>
> each account's **email** is its natural key at create time, aws forbids reuse, and it must
> never be committed — so all three arrive by env and **throw at module load** if absent. the
> eager throw is deliberate: a lazy getter would defer the failure into the middle of an apply,
> where a half-provisioned org is the cost of a typo.

**(a) the `jelly@one.nheuron.com` mail infra** — declared by **consumption of** the resource types
declastruct-aws already published, mirrored on `provision/aws.infra/account=demo/resources.mail.ts`
+ `provision/cloudflare/resources.mail.dns.ts`. applies into **`nheuron-prep`**.

> **how-to (read these first):** the demo ships readmes that walk the whole apply, prereqs, and
> the dns hand-off — the demonstration follows them step-for-step:
> - `provision/aws.infra/account=demo/readme.md` — prereqs + `apply --wish resources.mail.ts`
> - `provision/cloudflare/readme.md` — the mail dns records + how the dkim tokens flow from the
>   ses apply log into the dns file
> the resource declarations to mirror:

```
# aws side (declastruct-aws — already published, we consume them) — applies into nheuron-prep
DeclaredAwsSesEmailIdentity              identity = one.nheuron.com  # v2 easy-dkim; emits 3 cname tokens
DeclaredAwsS3Bucket                      name     = <mail-inbound bucket, globally unique>
DeclaredAwsS3BucketPolicy                bucket   = ^                # allow ses.amazonaws.com PutObject (SourceAccount+SourceArn scoped)
DeclaredAwsSesReceiptRuleSet             name     = <rule-set>       # active set (one per region)
DeclaredAwsSesReceiptRule                name     = to-s3            # recipient = jelly@one.nheuron.com ONLY → s3 put, prefix=inbound/
DeclaredAwsIamRole + …RolePolicyAttachedInline   # dedicated role; s3:GetObject on that prefix + ses:SendRawEmail scoped *@one.nheuron.com
DeclaredAwsSesConfigurationSet + …EventDestination  # send-event capture → cloudwatch
DeclaredAwsSesAccountDetails             productionAccess = enabled  # sandbox exit

# dns side (declastruct-cloudflare — replicated from the demo dns file, NOT manual)
DeclaredCloudflareDomainZone             name = nheuron.com
DeclaredCloudflareDomainDnsRecord ×6     # MX (inbound) + SPF TXT + 3 dkim CNAMEs + DMARC TXT, all proxied:false
```

(the read-only `DeclaredAwsIamPolicy` dao is a non-issue: the demo expresses the grant as an
**inline role policy** — `DeclaredAwsIamRolePolicyAttachedInline` — which is writable.)

**(b) gatherer `ses` adapter** — the first caller of that infra, both directions:

```
getSesMailAdapter          # implements GatherMailAdapter (read)
  getAllMailFromSes        #   s3 ListObjectsV2 + GetObject, parse raw rfc822 (mailparser)
  getGatheredMailFromSes   #   raw rfc822 → GatheredMail (exid = s3 key = ses messageId)
setReplyViaSes             # send: ses:SendRawEmail (the respond path)
getSesAuthAdapter          # iam status via sts:GetCallerIdentity (no oauth, no expiry)
```

**(c) the demonstration** — dogfood the whole loop end-to-end on the real `jelly@one.nheuron.com`
mailbox (the same shape declastruct-aws proved with `echo@demo.ehmpathy.com`):

```sh
# 0. BY HAND (once): create nheuron-root + its aws organization  — per bootstrap.md
# 1. apply the account wish AS THE ROOT → nheuron-prod + nheuron-prep are minted
# 2. assume into nheuron-prep, apply the mail wish (ses + s3 + iam) there
# 3. apply the cloudflare dns wish → mx + spf + 3 dkim cnames + dmarc; await propagation
# 4. send a test email TO jelly@one.nheuron.com → it lands in the s3 inbound/ bucket
# 5. rhx gather.mail --from ses --address jelly@one.nheuron.com → the email appears, parsed
# 6. reply FROM jelly@one.nheuron.com via setReplyViaSes → recipient receives it
```

this is the proof the vision now *can* stand on — a live mailbox, not a stub — because the
resources are published and the demo shows the pattern works.

**the parameters (both deliverables share):**

| param | purpose | demo (shipped) | demonstration (this behavior) |
|-------|---------|----------------|-------------------------------|
| `<account>` | the aws account the mail applies into | `ehmpathy-demo` | `nheuron-prep` |
| `<mail-domain>` | the subdomain provisioned for mail | `demo.ehmpathy.com` | `one.nheuron.com` |
| `<mailbox>` | a local-part on that domain | `echo@demo.ehmpathy.com` | `jelly@one.nheuron.com` |
| `<region>` | ses-inbound-capable region | `us-east-1` | `us-east-1` |
| `<zone>` | cloudflare zone that holds the dns | `ehmpathy.com` | `nheuron.com` |

> **address shape = subdomain (settled).** the demonstration uses the **subdomain**
> `one.nheuron.com` (mailbox `jelly@one.nheuron.com`), exactly as the demo used
> `demo.ehmpathy.com` — this keeps the `nheuron.com` apex mx free for whatever else the domain
> serves and isolates the blast radius. the zone `nheuron.com` holds the records (as
> `ehmpathy.com` holds `demo.ehmpathy.com`'s).

### what it looks like to leverage

once the infra is applied, the steady-state loop is two commands:

```sh
# read: collect the mail sent to jelly
rhx gather.mail --from ses --address jelly@one.nheuron.com --since 2026-08-01
#   → each mail appears, parsed (from, subject, snippet); security-sensitive ones obfuscated

# send: answer one, as jelly
#   → setReplyViaSes → ses:SendRawEmail → messageId
```

### timelines

1. **bootstrap (by hand, once)** — create `nheuron-root` + its aws organization
2. **accounts** — apply the account wish as the root → `nheuron-prod` + `nheuron-prep` minted
3. **mail infra** — assume into `nheuron-prep`, apply the ses + s3 + iam wish there
4. **dns** — apply the cloudflare wish (declarative, not a manual paste); await propagation, at
   which point the domain identity moves from `unresolved` to verified
5. **auth-check** — `AWS_PROFILE` loads (sts:GetCallerIdentity) → authenticated
6. **read** — a test email to `jelly@one.nheuron.com` lands in s3, the gatherer parses it
7. **send** — jelly answers from the same address
8. **reuse** — re-run the same declared resources for the next clone's mailbox

## mental model

### how users describe it to a friend

"i gave my clone its own email address on a subdomain i own, via aws ses — mail comes in
through an s3 bucket, the clone answers through the ses api, and the whole thing is declared
as infra in its own locked-down aws account, so i can re-create or tear it down with one
command. no google workspace, no oauth."

### analogies

| familiar concept | maps to |
|-----------------|---------|
| terraform apply | declastruct apply for the mail resources |
| a postbox on a street you own | a mailbox on a subdomain you own |
| `aws configure` profile | `AWS_PROFILE` from keyrack (the mailbox's iam identity) |
| a mailroom that files letters | ses receipt rule → s3 bucket |
| `git fetch` + local archive | `gather.mail --from ses` + local cache |

## evaluation

### how well does it solve the goals?

| goal | coverage |
|------|----------|
| provision send+read email infra | ✓ via declared ses + s3 + iam resources |
| own a clone's mailbox without a workspace | ✓ via a domain we already own + ses |
| bidirectional (read AND send) | ✓ s3 read + `ses:SendRawEmail` |
| reusable across domains | ✓ every resource parameterized by mail-domain + mailbox |
| least-privilege auth | ✓ scoped iam policy, no delegation |
| reproducible + idempotent | ✓ declastruct get+set |
| **lockdown — nested isolation** | ✓ org → account → subdomain → mailbox → grant → obfuscated content, each an independent wall |

### pros

- **own the whole mailbox** — scoped to one address on a subdomain, in its own aws account
- **no oauth, no token expiry** — plain iam via `AWS_PROFILE`
- **bidirectional** — read and send from one identity
- **declared + idempotent** — reproducible, tear-down-able
- **reuses the gatherer contract** — `GatheredMail`, cache, obfuscation, output are intended shared with gmail (the rfc822 → `GatheredMail` field mapping — esp. labels/attachments, which rfc822 has no native concept of — is confirmed at blueprint, not asserted here)
- **cheap** — ses inbound + s3 storage is low-cost at a clone's mail volume

### cons

- **ses sandbox** — new accounts send only to verified addresses until production access is granted (the demo's `DeclaredAwsSesAccountDetails productionAccess=enabled` requests it; aws reviews async)
- **region-locked inbound** — ses receipt works in a subset of regions; mx + bucket must share it
- **poll, not push** — v1 reads s3 on demand; no live sns notify
- **dkim propagation lag** — the domain identity stays `verificationStatus: unresolved` until the (now declarative) cloudflare dns propagates; send/receive both wait on it
- **a by-hand bootstrap remains** — `nheuron-root` + its aws organization cannot be declared by the tool that authenticates as them, so one manual console step survives at the very bottom
- **the nested vaults cost real setup** — a whole org + 3 accounts + 2 credential sets to stand up one mailbox. accepted deliberately (`._.zoom=fort-knox-of-fort-knoxes`), but it is a genuine cost, not a free win
- **a second clone needs its own rule** — the receipt rule names one recipient, so mailbox #2 on the same subdomain is another declared rule rather than a shared catch-all

> **resolved since first draft** — three caveats the original vision carried are now gone:
> declastruct-aws **published** the s3 + ses resource types (no net-new authorship), the demo
> **proved** the whole stack live (`echo@demo.ehmpathy.com`), and dns is now **declarative** via
> `declastruct-cloudflare` (no manual paste). the demonstration can stand on a real mailbox.

### edgecases and pit of success

| edgecase | handle |
|----------|--------|
| infra not applied yet | auth-check fails loud (sts) with a hint to apply the `resources.mail.ts` wish |
| apex mx already serves other mail | sidestepped — the mail domain is a dedicated subdomain, so the `nheuron.com` apex mx is untouched |
| cloudflare proxies the mx/txt | the dns file declares every record `proxied: false` (dns-only) — a proxied record breaks mail |
| ses still in sandbox | `DeclaredAwsSesAccountDetails productionAccess=enabled` requests the exit; verify a test recipient meanwhile |
| bucket name collision (globally unique) | name keyed to the mail-domain (demo: `ehmpathy-mail-inbound-demo`) |
| cross-account write to the bucket | bucket policy condition `aws:SourceAccount` + `aws:SourceArn` = the receipt rule arn |
| least-privilege grant | inline role policy (`DeclaredAwsIamRolePolicyAttachedInline`, writable) — the read-only managed-policy dao is avoided |
| retire a mailbox | del the declared resources (idempotent) |

## open questions & assumptions

### assumptions

1. **scope = both + demonstrate, infra is REAL.** deliver the `jelly@one.nheuron.com` mail infra
   (consume the published declastruct-aws resources + replicate the demo's cloudflare dns) AND
   the gatherer `ses` adapter (read + send), THEN dogfood the whole loop on the live mailbox.
   the resources are published and demo-proven, so the demonstration stands on a real mailbox.
2. `jelly@one.nheuron.com` is the demonstration mailbox on a dedicated **subdomain**
   (`one.nheuron.com`), so the `nheuron.com` apex mx stays free — same shape as the demo.
3. `AWS_PROFILE` is available via keyrack (declared in `env.all`) ✓ — but the cloudflare
   credentials are **not** (see open question 5); they must be added before the dns can apply.
4. region `us-east-1` (ses-inbound-capable) unless told otherwise.
5. the clone's identity is one dedicated iam **role** behind `AWS_PROFILE` (the demo's choice).

### open questions — triaged

1. [answered] **identity** — dedicated iam **role** + inline grant. answered by the demo, which
   uses `DeclaredAwsIamRole` (`ehmpathy-mail-robot`) + `DeclaredAwsIamRolePolicyAttachedInline`,
   not an iam user or the ambient sso role.
2. [answered] **read-scope default** — a **single mailbox**, `jelly@one.nheuron.com`. the receipt
   rule names that one recipient, same as the demo's `echo@…`. reads no more than the clone needs.
3. [answered] **how to test** — dogfood on the **real** `jelly@one.nheuron.com` mailbox, the same
   integration/manual measurement the demo used (apply → send test email → gather → reply). the
   resources are published + demo-proven, so no stub is needed; the verification bar is a live loop.
4. [answered] **account** — provision a **new nheuron account triplet** (`nheuron-root`,
   `nheuron-prod`, `nheuron-prep`) rather than reuse the ehmpathy `demo` account. the mail infra
   applies into `nheuron-prep`. this adds deliverable (a0) — see above.
   **why a separate account:** the lockdown is the most important property of an external brain.
   a breach here is not "records leaked" — it is a copy of a person's cognition. so the substrate
   is built as a **fort knox made of fort knoxes**: org → account → subdomain → mailbox → grant →
   obfuscated content, each an independent wall. a shared account would collapse the outermost
   two. see `philosophy.external-brain._.zoom=fort-knox-of-fort-knoxes`.
5. [answered] **cloudflare credentials** — absent from this repo's keyrack today (verified against
   `.agent/keyrack.yml`: `AWS_PROFILE` in env.all, no cloudflare keys). the wisher will load them
   when the dns step is reached. needs a cloudflare **user** token (My Profile > API Tokens, not
   an account token) with Zone:Read + DNS:Edit, plus the account id.
6. [answered] **`nheuron.com` zone** — yes, we own it. the dns records apply into that zone.
7. [best-guess] **where the provision files live** — this repo, not declastruct-aws. precedent:
   `provision/github.repo/resources.ts` already declares this repo's own resources by consumption
   of `declastruct-github`. so the mail wish follows the same shape — `provision/aws.mail/` +
   `provision/cloudflare/` here — and declastruct-aws stays a published dependency rather than
   the home for nheuron-specific infra. flagged as a clean rework if the wisher prefers otherwise.
8. [answered] **dns is declarative, not manual** — `declastruct-cloudflare` now exists and the
   demo replicates its full dns set (`provision/cloudflare/resources.mail.dns.ts`). the
   demonstration replicates that file for `nheuron.com` — the only hand-sourced input is the 3
   dkim tokens the ses identity emits at apply time.
9. [answered] **address shape** — a dedicated **subdomain** (`one.nheuron.com`, mailbox
   `jelly@one.nheuron.com`), same as the demo's `demo.ehmpathy.com`. keeps the apex mx free.
   the `one.` label is a **domain term**, not a numeral — see the etymology below.
10. [answered, by research] **`nheuron-root` is its own account AND the organization manager.**
    resolved against a peer repo that runs this exact triplet. the shape:
    - `nheuron-root` = the org's **management** account. it is **bootstrapped by hand**, never
      declared — a human creates the account, then clicks "Create an organization" in the aws
      console (there is a `bootstrap.md` for precisely this). declastruct cannot mint the org it
      authenticates as.
    - `nheuron-prod` + `nheuron-prep` = declared **member** accounts, each a
      `DeclaredAwsOrganizationAccount` whose `organization.managementAccount` refs the root's id
      (read at apply time from the provider's own credentials).
    - so the apply runs **as the root**, and mints the other two.
    research note: declastruct-aws's `resources.root.account.ts` is NOT an account declaration —
    it declares **SCPs** attached to the org root. "root.account" names *where the resources
    live*, not a declared account.
11. [answered, by research] **account emails come from env, never a literal.** an aws account's
    root email is its natural key at create time and must never be committed. the peer pattern:
    a dedicated module of module-level constants, each `process.env.X ?? UnexpectedCodePathError
    .throw(...)`, kept **apart** from the shared policy module for two documented reasons:
    - they **throw at module load** (deliberately eager) — a lazy getter would defer the failure
      into the middle of an apply, "where a half-provisioned org is the cost of a typo"
    - co-location would make every policy bundle unimportable without the full account env,
      which broke unit tests that touch policy shape alone
    only the root dir mints accounts, so only the root dir pays the env cost. the concrete
    addresses are a fill-time input, not a blueprint decision.

## groundwork

### external research

**aws ses inbound + s3** — verified against aws docs + the handoff groundwork:
- ses receipt routes inbound mail via an mx record to `inbound-smtp.<region>.amazonaws.com`,
  then a receipt rule stores raw rfc822 to s3 ✓
- ses inbound receipt is region-limited (e.g. `us-east-1`, `us-west-2`, `eu-west-1`) ✓
- v2 easy-dkim emits 3 cname tokens and proves ownership via those cnames alone — there is NO
  separate `_amazonses` TXT (that was the v1 shape; confirmed by the demo provision note) ✓
- new ses accounts start in the sandbox (verified recipients only) until production access ✓
- `ses:SendRawEmail` sends from a verified domain identity ✓

docs: https://docs.aws.amazon.com/ses/latest/dg/receiving-email.html

**cloudflare dns** — mx/txt/cname records must be dns-only (not proxied) for mail to flow ✓

### internal research

**gatherer contract** — verified against this repo (the gmail behavior already built it):
- `GatheredMailMechanism` (`src/domain.objects/GatheredMailMechanism.ts`) — literal
  `'gmail' | 'slack' | 'phone'`; needs `'ses'` added; `VALID_MECHANISMS = ['gmail']` needs `'ses'` ✓
- `GatherMailAdapter` (`src/domain.objects/GatherMailAdapter.ts`) — interface the ses adapter
  implements: `getAllMail(input, { log, accessToken })` → `{ mails, stats, page }` ✓
- adapter dispatch: `getMailAdapterForMechanism.ts` / `getAuthAdapterForMechanism.ts` gain an
  `ses` branch ✓
- the gmail adapter (`src/domain.operations/gather/adapters/gmail/`) is the reference shape
  the ses adapter mirrors ✓

**declastruct-aws (published + dogfooded)** — verified against `src/access/daos/` on
`origin/main`:
- **s3 published**: `DeclaredAwsS3BucketDao`, `DeclaredAwsS3BucketPolicyDao` ✓
- **ses published**: `DeclaredAwsSesEmailIdentityDao`, `DeclaredAwsSesReceiptRuleDao`,
  `DeclaredAwsSesReceiptRuleSetDao`, `DeclaredAwsSesConfigurationSetDao`,
  `DeclaredAwsSesConfigurationSetEventDestinationDao`, `DeclaredAwsSesAccountDetailsDao` ✓
- **iam (reuse)**: `DeclaredAwsIamRole` + `DeclaredAwsIamRolePolicyAttachedInline` (writable);
  the managed-policy `DeclaredAwsIamPolicy` dao is read-only, so the demo uses the inline grant ✓
- **the working dogfood** — `provision/aws.infra/account=demo/resources.mail.ts` (287 lines)
  stands up `echo@demo.ehmpathy.com`: identity → bucket → bucket-policy → rule-set → rule →
  role + inline grant → config-set + event-dest → account-details. this is the exact template

**the account triplet** — verified against a peer repo that already runs a `-root` / `-prod` /
`-prep` org:
- the org's **management** account is bootstrapped **by hand** (a `bootstrap.md` walks the
  console steps: create the account, then "Create an organization"); declastruct cannot mint the
  org it authenticates as ✓
- each **member** account is a `DeclaredAwsOrganizationAccount` whose
  `organization.managementAccount` refs the root id read at apply time from the provider's own
  credentials; `roleName: 'OrganizationAccountAccessRole'` is the assume path ✓
- account root **emails** live in their own module as module-level constants that throw at load
  when absent — deliberately eager, so a typo fails before an apply rather than halfway through

  **SCPs** attached to the org root. "root.account" names where the resources live ✓

### what is awkward?

**the apply seam remains async.** the resources are declared + idempotent, but a domain
identity stays `verificationStatus: unresolved` until the (now declarative) cloudflare dns
propagates. so the apply is: ses identity first (emits dkim tokens) → cloudflare records →
wait for propagation → verified. the demo splits this cleanly (the dkim tokens are the sole
hand-sourced input to the dns file), but the demonstration's "receive a real email" step still
waits on dns propagation — a real-world delay, not an instant loop.

**the `one.` label reads as a numeral to outsiders.** within nheuron it is a domain term —
`clone` → drop the `cl` → `one`, and a `one` IS a clone: one neuron connection into the external
brain. so `jelly@one.nheuron.com` reads *jelly, a clone, one connection into the external brain*.
but a reader outside the domain may parse it as "instance #1". we accept that cost because
ubiqlang says the domain's own word wins over a generic outsider label — and the term is now
documented rather than folklore. reversal is cheap in the infra (a rename in the two provision
files plus a dns re-apply), though the briefs would need an update too.

> **enbriefed** — the term and the worldview behind it are recorded, so this vision cites rather
> than restates them:
> - `domain.terms/one.md` — the **term**: full etymology, the wisher's narrative as evidence,
>   precedent from the extant `clone` dobj, invariants
> - `philosophy.clones-not-bots.md` — why the word decides the architecture (`bot` implies

>   arguments, and where it applies beyond this one term
> - `philosophy.external-brain.md` + `._.zoom=wetware-bandwidth` + `._.zoom=fort-knox-of-fort-knoxes`
>   — what the brain IS, the seam this widens, and why the lockdown nests (the reason for the
>   dedicated account triplet)

**single-mailbox forgoes the general "read all mail for the domain" case.** a domain-wide
catch-all would be the more general fit, but it reads *every* address on the subdomain — more
than one clone needs, and a wall dissolved (`._.zoom=fort-knox-of-fort-knoxes`). so the receipt
rule names `jelly@one.nheuron.com` alone. the cost is honest: a second clone on the same
subdomain needs its own rule rather than a shared catch-all. that is the intended trade.
