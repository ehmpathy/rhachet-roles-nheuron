# vision: collect-from-gmail

---

## amendment: ses mechanism (bidirectional mail)

> added after the gmail-first vision below. gmail is readonly-collect only; ses adds a
> second mechanism that is **bidirectional** — collect (receive) AND respond (send).

### why ses

gmail's service-account path needs google workspace + domain-wide delegation, which grants
a service account access to *every* mailbox in the org — too broad for a robot. instead we
stand up a dedicated robot mailbox on a domain we already own (`ehmpath.com`, on cloudflare)
via **aws ses**:

- **receive** — mx record routes inbound mail → ses → an s3 bucket (raw rfc822). the
  adapter reads + parses from s3. no oauth, no per-mailbox delegation.
- **send** — the robot can *respond*. `ses:SendRawEmail` via the aws sdk, from the same
  verified domain.
- **auth** — iam via `AWS_PROFILE` (already available from keyrack, same as
  rhachet-roles-ghlitch skills). no oauth dance, no 7-day token expiry.

### day-in-the-life (ses)

```sh
# collect mail sent to the robot mailbox (address is a dedicated mail subdomain)
rhx gather.mail --from ses --address robot@mail.ehmpath.com

# (future skill) respond to a gathered mail
rhx gather.reply --from ses --address robot@mail.ehmpath.com --to alice@example.com
```

> **address shape**: ses uses a dedicated **mail subdomain** (`mail.ehmpath.com`), not the
> apex — keeps the apex mx free and isolates blast radius. test domain: `demo.ehmpathy.com`.

### mechanism comparison

| dimension | gmail | ses |
|-----------|-------|-----|
| direction | receive only | receive + send |
| auth | oauth device flow, 7-day token (test mode) | iam via `AWS_PROFILE`, no expiry |
| receive path | gmail api (list + get) | mx → ses → s3, read raw rfc822 |
| send path | n/a | `ses:SendRawEmail` sdk |
| address | `vlad@gmail.com` | `robot@mail.ehmpath.com` (mail subdomain) |
| setup | user's gcp project | aws ses + cloudflare dns (see handoff) |
| account scope | one user's inbox | a domain mailbox we own |

### what stays the same

ses is just another adapter behind the same dispatcher. `GatheredMail`, the cache layout,
the security-obfuscation rule, the tree/json output, incremental sync — all reused. the
`GatheredMailMechanism` literal gains `'ses'`; `getMailAdapterForMechanism` gains an `ses`
branch. everything downstream is mechanism-agnostic.

### security note (why ses over gmail service account)

the gmail service-account route (workspace domain-wide delegation) grants the service
account impersonation of *any* user in the org — a broad blast radius for a robot. a
dedicated ses domain mailbox is scoped to exactly the addresses on that domain, no more.
this is the safer default for automated collection.

## the outcome world

### day-in-the-life

vlad starts his day. instead of context-switch to gmail tabs, juggle browser windows, he runs:

```sh
rhx gather.mail --from gmail --address vlad@gmail.com
```

a stream of thoughts and todos flows into his terminal — subject lines, senders, snippets. the first run fetches from gmail api and caches locally. subsequent runs are instant — local disk lookup, no network. incremental sync is the default — only new emails since last sync. he scans, captures what matters, moves on.

later, he adds:
```sh
rhx gather.mail --from slack --address ehmpathy
```

async comms from all sources flow into one stream. gmail, slack, phone — all "mail" in the collector's view.

| before | after |
|--------|-------|

| scroll through inbox manually | stream filtered emails to terminal |

## user experience

### usecases

| usecase | goal |
|---------|------|
| inbox scan at start of day | see what arrived overnight without open browser |
| instant local lookup | query cached emails without network latency |
| todo extraction | collect emails that contain action items |
| search across time | find that email from last week with the link |
| safe terminal display | view emails without expose mfa codes |
| incremental sync | only fetch new emails since last sync |

### contract inputs & outputs

**skill 1: gather.auth** — oauth flow → token storage

```sh
# initiate oauth flow for gmail
rhx gather.auth --from gmail

# opens browser for google consent
# stores tokens in keyrack os.secure under email address
```

input: source (gmail, slack, phone — gmail for v1)
output: tokens stored in keyrack under `GATHER_SOURCE_{source}_ADDRESS_{hashOf(address)}` pattern

**skill 2: gather.mail** — fetch and cache emails readonly

```sh
# default: incremental sync (new emails since last sync)
rhx gather.mail --from gmail --address vlad@gmail.com

# explicit: same as default
rhx gather.mail --from gmail --address vlad@gmail.com --since sync

# fetch emails since specific date
rhx gather.mail --from gmail --address vlad@gmail.com --since 2026-04-22

# fetch with query filter
rhx gather.mail --from gmail --address vlad@gmail.com --query "from:boss@company.com"

# output format options
rhx gather.mail --from gmail --address vlad@gmail.com --format json
rhx gather.mail --from gmail --address vlad@gmail.com --format tree
```

input: source, email address, optional since filter (date or "sync"), optional query
output: email summaries (id, from, subject, snippet, date) — from local cache

**cache behavior**:
- first run: fetch from gmail api, store in local cache
- subsequent runs: return from local cache, no network
- default (`--since sync`): only fetch emails newer than last sync timestamp
- cache invalidation: not needed — emails are immutable once received

### timelines

1. **first run**: `gather.auth --from gmail` opens browser, user consents, tokens stored (~30 seconds)
2. **first sync**: `gather.mail` fetches all emails, stores in local cache (~varies by inbox size)
3. **subsequent runs**: `gather.mail` fetches only new emails (default: `--since sync`), instant local query
4. **every 7 days** (test mode): token expires, user runs `gather.auth --from gmail` again
5. **future** (verified app): no 7-day expiration

## evaluation

### how well does it solve the goals?

| goal | coverage |
|------|----------|
| collect thoughts from gmail | ✓ via `gather.mail --from gmail` |
| instant local query | ✓ via local cache |
| incremental sync | ✓ via default (`--since sync`) |
| secure token storage | ✓ via keyrack os.secure |
| readonly safety | ✓ via gmail.readonly scope |
| obfuscate sensitive emails | ✓ via pattern detection |
| extensible to other sources | ✓ via `--from {gmail,slack,phone}` pattern |

### pros

- **local-first** — queries hit local disk, instant response
- **incremental sync** — only fetch new emails, reduce api calls
- **readonly by design** — gmail.readonly scope, no accidental modifications
- **secure token storage** — age-encrypted in os.secure, never plaintext
- **sensitive content protection** — mfa/password emails auto-obfuscated
- **terminal-native** — no browser context switches
- **composable** — output can pipe to other tools
- **extensible** — `--from` pattern supports future sources (slack, phone)

### cons

- **7-day token expiration** — test mode limitation, requires re-auth weekly
- **two-step api** — messages.list returns only IDs, must call messages.get for content
- **initial sync time** — first run must fetch all emails (can be slow for large inboxes)
- **disk usage** — local cache grows with email volume
- **google verification eventually needed** — for production use without expiration

### edgecases and pit of success

| edgecase | handle |
|----------|--------|
| token expired | clear error: "token expired, run gather.auth --from gmail" |
| no emails match query | empty result, not error |
| email contains "password" in subject | entire email obfuscated |
| email is mfa code | obfuscated, only existence shown |
| rate limit hit | retry with backoff, inform user |
| user revoked access | clear error, prompt re-auth |
| cache corrupted | detect via checksum, re-sync affected range |
| duplicate email id | skip — email already cached |
| email deleted remotely | keep in cache — emails are immutable snapshots |

## what is awkward?

### 7-day re-auth dance

the test mode 7-day expiration is friction. users will need to re-run `gather.auth --from gmail` weekly. this is google's guardrail, not ours, but it still feels clunky.

**mitigation**: clear message when token expires, one-command re-auth.

### two-api-calls per email

gmail api requires list → get flow. we can't get full email content in one call. this means more network round trips.

**mitigation**: batch messages.get calls, parallelize where possible. local cache means this cost is paid once per email, not per query.

### "am i really secure?"

users may wonder if obfuscation is enough. what if the pattern misses some item?

**mitigation**: conservative patterns, err on side of obfuscate too much. clearly document what triggers obfuscation.

**future**: spawn local brain atom to ask "is this sensitive?" for smarter detection beyond keyword patterns.

### google cloud project setup

users need a gcp project with gmail api enabled. this is a one-time hurdle but adds friction.

**mitigation**: each adapter supplies fluid guidance in `gather.auth` stdout — walks user through setup step by step.

### initial sync time

first run could fetch all emails from gmail. for large inboxes, this could take minutes.

**mitigation**: require `--since` on first run (e.g., `--since -1mo`). user controls scope. subsequent runs default to `--since sync`.

## cache design (critical)

### uniqueness

cache key = `{source}/{address}/{message_id}`

gmail message ids are:
- globally unique
- stable (don't change over email lifetime)
- returned by messages.list

### storage layout

```
.agent/.cache/repo=nheuron/role=collector/skill=gather.mail/
  └─ source=gmail/
     └─ address=vlad@gmail.com/
        ├─ .sync.json         # metadata: lastSync, historyId, totalCached
        └─ emails/
           ├─ email.exid=18f3a2b4c5d6e7f8.json
           ├─ email.exid=18f3a2b4c5d6e7f9.json
           └─ email.exid=18f3a2b4c5d6e7fa.json
```

**why one file per email?**
- direct lookup by exid: no scan required
- idempotent write: overwrite if exists
- filesystem is the index
- glob for iteration: `emails/email.exid=*.json`

### sync state

```json
{
  "lastSync": "2026-04-23T10:30:00Z",
  "historyId": "12345678",
  "totalCached": 47
}
```

### invalidation

none needed. emails are immutable:
- once received, content doesn't change
- labels might change, but we only cache content
- deleted emails stay in cache (they're snapshots)

### query flow

1. `gather.mail` (default: `--since sync`)
2. read `.sync.json` for last historyId
3. call gmail api: `users.history.list(startHistoryId)`
4. for each message id: skip if already cached, else call `messages.get` and store
5. update `.sync.json`
6. return results from cache

**idempotent**: list may return ids we already have — skip the `.get` call for those. safe to re-run.

### future: cross-source

```
.agent/.cache/repo=nheuron/role=collector/skill=gather.mail/
  ├─ source=gmail/address=vlad@gmail.com/
  ├─ source=slack/address=ehmpathy/
  └─ source=phone/address=+1-555-1234/
```

same pattern applies: `source={source}/address={address}/`

### address as extensible path

address can narrow scope via path-like syntax:

| source | address | scope |
|--------|---------|-------|
| gmail | `vlad@gmail.com` | whole inbox |
| gmail | `vlad@gmail.com/labels=work,urgent` | label-filtered |
| slack | `ehmpathy` | whole workspace |
| slack | `ehmpathy/channel=general` | specific channel |
| phone | `+1-555-1234` | all messages |

this enables `--address` to stay unified while each `--from {source}` parses and elaborates its own address space.

### architecture: dispatcher + adapters

`gather.mail` is a common dispatcher. each source supplies an adapter:

```
gather.mail --from gmail --address ...
     │
     └─► dispatcher
           │
           ├─► adapter.gmail   (oauth, gmail api, email address parsing)
           ├─► adapter.slack   (oauth, slack api, workspace/channel parsing)
           └─► adapter.phone   (sms gateway, phone number parsing)
```

adapters handle:
- address parsing (source-specific format)
- authentication (oauth, api keys, etc.)
- api calls (fetch, sync, cache)
- output normalization (common mail format)
