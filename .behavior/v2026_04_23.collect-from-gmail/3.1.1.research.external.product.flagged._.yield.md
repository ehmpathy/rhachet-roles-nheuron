# research: vision-flagged topics

the vision flagged four topics for research:
1. exact oauth flow for desktop apps (loopback redirect, device flow, etc)
2. google cloud console project setup steps for users
3. whether we can use installed app credentials vs user brings their own
4. gmail message id stability guarantees (for cache uniqueness)

---

## topic.1 = oauth flow for desktop/cli apps

### sources

1. [official] [OAuth 2.0 for iOS & Desktop Apps](https://developers.google.com/identity/protocols/oauth2/native-app) — Google for Developers
2. [official] [Loopback IP Address flow Migration Guide](https://developers.google.com/identity/protocols/oauth2/resources/loopback-migration) — Google for Developers
3. [official] [Making Google OAuth interactions safer](https://developers.googleblog.com/making-google-oauth-interactions-safer-by-using-more-secure-oauth-flows/) — Google Developers Blog
4. [official] [Out-Of-Band (OOB) flow Migration Guide](https://developers.google.com/identity/protocols/oauth2/resources/oob-migration) — Google for Developers
5. [practitioner] [OAuth2 Gmail IMAP for installed applications](https://www.limilabs.com/blog/oauth2-gmail-imap-installed-applications) — Limilabs Blog
6. [practitioner] [GitHub: Device Flow for headless CLI](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) — GitHub Docs
7. [official] [Setting up OAuth 2.0](https://support.google.com/googleapi/answer/6158849?hl=en) — Google API Console Help

### claims

**[FACT]** loopback flow is supported for desktop apps
> "the loopback IP address flow is being deprecated for the native iOS, Android, and Chrome OAuth client types but will continue to be supported on desktop apps"
— source [2]

**[FACT]** loopback flow is vulnerable to mitm attacks
> "The Loopback IP address flow is vulnerable to man in the middle attack where a malicious app, accessing the same loopback interface on some operating systems, may intercept the OAuth response"
— source [3]

**[FACT]** device flow exists for limited-input devices
> "The device flow supports applications that run on limited-input devices. The authorization sequence begins with the application making a web service request to a Google URL for an authorization code."
— source [1]

**[FACT]** device flow works for cli tools
> "device flow allows you to authorize users for a headless application, such as a CLI tool"
— source [6]

**[FACT]** oob flow is deprecated
> "if you determine that your app is using the OOB flow on a desktop client, you should migrate to using the loopback IP address (localhost or 127.0.0.1) flow"
— source [4]

**[SUMP]** localhost may cause firewall issues
> "It is also possible to use localhost in place of the loopback IP, but this configuration may cause issues with client firewalls"
— source [4]

**[KHUE]** which flow is best for cli: loopback or device?
- loopback requires local server, has mitm vulnerability on some os
- device flow is more secure, works headless, but requires user to switch devices

### convergence

sources [1], [2], [3], [4] all agree: loopback flow is supported for desktop but has security concerns; device flow is the more secure alternative for cli/headless apps

### recommendation

[OPIN] for a cli tool like gather.auth, device flow is preferable:
- works in headless environments (ssh, wsl, docker)
- no local server required
- more secure (no mitm vulnerability)
- fallback: loopback flow for environments where device flow is awkward

## topic.3 = installed app credentials vs user-provided

### sources

1. [official] [Use OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2) — Google for Developers
2. [official] [Setting up OAuth 2.0](https://support.google.com/googleapi/answer/6158849?hl=en) — Google API Console Help
3. [official] [Credentials, access, security, and identity](https://support.google.com/googleapi/answer/6158857?hl=en) — Google API Console Help
4. [tutorial] [Set up an OAuth client](https://gmailr.r-lib.org/articles/oauth-client.html) — gmailr R package docs
5. [tutorial] [Google OAuth2 generic](https://docs.n8n.io/integrations/builtin/credentials/google/oauth-generic/) — n8n Docs
6. [tutorial] [Connect to Google services with a custom OAuth client](https://help.make.com/connect-to-google-services-using-a-custom-oauth-client) — Make Help Center
7. [practitioner] [GitHub issue: Google Refresh Token expiration](https://github.com/activepieces/activepieces/issues/3067) — activepieces

### claims

**[FACT]** each user can create their own oauth client
> "To use OAuth 2.0 in your application, you need an OAuth 2.0 client ID, which your application uses when it requests an OAuth 2.0 access token"
— source [1]

**[FACT]** installed app credentials exist
> "Different application types, such as web server, installed, client-side, limited-input device, and service accounts, have specific authorization flows"
— source [1]

**[SUMP]** shared credentials have limits
- unverified apps have 7-day token expiration
- unverified apps have 100 user limit in test mode
- verified apps require google review process

**[KHUE]** should we provide shared credentials or require user-provided?

### tradeoffs

| approach | pros | cons |
|----------|------|------|
| shared credentials | zero setup for users | 7-day expiration in test mode; 100 user limit; verification required for production |
| user-provided | no expiration limits; no user limits | requires gcp project setup |

### convergence

sources [4], [5], [6] all guide users to create their own oauth credentials — this is the common pattern for developer tools

### recommendation

[OPIN] require user-provided credentials for v1:
- avoids verification process
- no user limits
- no shared credential security concerns
- future: could provide shared verified credentials after google review

## topic.4 = gmail message id stability guarantees

### sources

1. [official] [REST Resource: users.messages](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages) — Google for Developers
2. [official] [Message class](https://googleapis.dev/java/google-api-services-gmail/latest/com/google/api/services/gmail/model/Message.html) — Google Java API docs

4. [practitioner] [Dates in Hid Part 3 — Gmail Message ID](https://www.metaspike.com/dates-gmail-message-id-thread-id-timestamps/) — Metaspike
5. [practitioner] [Message IDs Explained](https://learn.emailengine.app/docs/advanced/ids-explained) — EmailEngine docs
6. [official] [Python gmail_v1.users.messages](https://developers.google.com/resources/api-libraries/documentation/gmail/v1/python/latest/gmail_v1.users.messages.html) — Google Python API docs
7. [official] [C# Message class](https://developers.google.com/resources/api-libraries/documentation/gmail/v1/csharp/latest/classGoogle_1_1Apis_1_1Gmail_1_1v1_1_1Data_1_1Message.html) — Google C# API docs

### claims

**[FACT]** message id is immutable
> "The immutable ID of the message"
— source [1], [2], [3], [6], [7] (identical phrasing across all official api docs)

**[FACT]** message ids are unique per message
> "While the Message IDs are unique, the Thread IDs are not"
— source [4]

**[FACT]** message ids are hexadecimal, 15-16 digits
> "Both message and thread IDs are represented in hexadecimal form, along the lines of 1736ccf5d7b4d452. Gmail Message IDs can be 15 or 16 digits long"
— source [4]

**[SUMP]** message id does not change across operations
> inferred from "immutable" designation in official docs

**[KHUE]** are there edge cases where message id could change?
- no sources document any edge cases
- "immutable" is strong language in official docs

### convergence

strong convergence: 5 official google sources [1], [2], [3], [6], [7] all use identical phrasing: "The immutable ID of the message"

### recommendation

[OPIN] gmail message id is safe to use as cache key:
- official docs explicitly call it "immutable"
- unique per message
- stable across operations
- no documented edge cases

7. [practitioner] [Fetch multiple Gmail messages via API batch request](https://community.latenode.com/t/fetching-multiple-gmail-messages-using-api-batch-request/11193) — Latenode Community

### claims

**[FACT]** messages.list returns only ids
> "The messages.list method returns only message IDs. To get full message details, you need to call messages.get"
— source [2]

**[FACT]** batch requests support up to 100 calls
> "You're limited to 100 calls in a single batch request"
— source [1]

**[FACT]** batches larger than 50 not recommended
> "Send batches larger than 50 requests is not recommended"
— source [1]

**[FACT]** pagination supports up to 500 results per page
> "maxResults parameter (defaults to 100, maximum 500)"
— source [3]

### recommendation

[OPIN] for efficient sync:
1. use messages.list with maxResults=500 for pagination
2. batch messages.get calls in groups of 50
3. skip .get for already-cached message ids (idempotent)
