# 🌙 dream: the first caller of `sendReplyViaSes` owes a sent-marker

kind: gather · owner: this repo · caught 2026-11-01

## .the cue that fired

peer r7 at i002 of stone `5.1` (nitpick.1): `SendRawEmail` is an append, and no guard in code
stops a retry from a second send.

## .the gap, precisely

`sendReplyViaSes` is the one non-idempotent operation in the behavior. its doc names the hazard
and it has no caller today, so no retry path exists yet. the guard is owed the day one does.

## .the shape of the fix

- a per-mail sent-marker beside the mail cache, keyed on the `inReplyTo` message id
- the caller checks the marker, sends, then writes the marker with the returned `messageId`
- a clamp: a second call with the same `inReplyTo` returns the recorded `messageId`, no send

## .why it is not done in this round

no caller exists, and the guard's key depends on what the first caller answers. a guard built
before its caller is a guess (`rule.prefer.wet-over-dry`).
