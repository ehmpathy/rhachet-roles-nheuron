# 🌙 dream: throw ConstraintError / MalfunctionError natively, so the thrown class is the reported one

kind: refactor · owner: this repo · caught 2026-11-02

## .the cue that fired

5.3 has-ergonomics-validated: every cli refusal reads `✋ ConstraintError: BadRequestError: …`.
two class names in one header (fulcrum F16).

## .the gap, precisely

`helpful-errors` is pinned at 1.5.3, which has no `ConstraintError` or `MalfunctionError`. the
code throws `BadRequestError` / `UnexpectedCodePathError`; `getExitCodeForError` prepends the
qualified class and `asErrorHeaderDetail` cuts the thrown class out of the message. the human
header is right today; the code still throws one class and reports another, and the cut
leans on the library's message format.

## .the shape of the fix

1. `rhx set.package.upgrade --package helpful-errors --to 1.7.6`
2. `rhx sedreplace` `BadRequestError` → `ConstraintError` and `UnexpectedCodePathError` →
   `MalfunctionError` across `src/` and `provision/` (imports, throws, `instanceof`, tests)
3. `getExitCodeForError` branches on the native classes; `asErrorHeaderDetail` goes if the
   library's own message reads `ConstraintError: <what>`
4. the stderr a human reads is already one-class (5.3), so the snapshots should not move

## .why it is not done in this round

a dependency bump plus a rename across every throw site is its own change. the part a human
sees (one class per header) already landed in 5.3 (fulcrum F16).
